# Design

DCP creation tool. Rust core with CLI and Tauri GUI.

## Layout

- `rust/crates/dcpwizard-core`: DCP assembly (CPL/PKL/ASSETMAP writers, MXF wrapping via postkit/asdcplib), encryption, KDM, export, job queue.
- `rust/crates/dcpwizard-cli`: clap CLI (create, encode, pipeline, kdm, certificate, verify, batch/daemon, serve, dashboard, ...).
- `gui/`: Tauri app; builds run through postkit::pipeline with the CLI as sidecar.
- Shares code via postkit (path dep at `extern/postkit`), asdcplib-rs (git), and dcpdoctor-core (git) for verify/info/report.
- Shared GUI code lives in guikit (`extern/guikit`), not in postkit, which must stay free of a tauri dependency because the CLI and wasm use it too. The preview server, the preview surface hosts, `preview.js` and `shortcuts.js` are guikit's, and both wizards depend on it and register its commands.
- CPL/PKL/ASSETMAP/VOLINDEX XML, `escape_xml`, and SRT parsing come from `postkit::packaging` / `postkit::subtitle_retime` (the app maps its configs onto those writers; no hand-rolled XML remains in cpl/pkl/assetmap).
- `~15` core modules are thin `pub use postkit::...` re-export shims.

## What is implemented and wired

- OV creation from video files or J2K dirs + WAV: demux, J2K encode (grok in-process FFI), real asdcplib MXF wrapping, CPL/PKL/ASSETMAP/VOLINDEX generation, SHA-1 hashes. Declared picture geometry always comes from the essence: `cpl::picture_geometry` reads the coded raster back from the first codestream's SIZ marker, and MainPictureStoredArea plus ScreenAspectRatio declare that raster (the same ratio postkit writes into the picture MXF descriptor). `create --container` (2K/4K scope, flat, full) and `create --container-dims WxH` (positive, even, within the 2K 2048x1080 / 4K 4096x2160 bound) declare the active area instead: the rectangle inside the frames a projector masks to, written as MainPictureActiveArea and defaulting to the whole raster. A container larger than the coded raster is refused, since ST 429-16 and libdcp's INVALID_MAIN_PICTURE_ACTIVE_AREA both require the active area to fit inside the picture.
- Pre-build check and hints (CORE/preflight.rs, CORE/hints.rs, `create --check`, GUI "Before you build" dialog). The rule is that a refusal the packager can make after the encode must also fire before it: `preflight::CreatePlan` is one description of a `create` job as both front ends settle it before any frame is compressed, and `preflight::check_before_encode` runs every refusal over it in one order. Each rule still lives with the code that owns it and is called from both ends, so the message exists once: `cpl::check_active_area_fits` (the container has to fit inside the coded raster, now predictable from `source_picture::resolve_picture`'s plan output), `pad::check_frame_aligned_sample_rate` (sample rate a whole number of samples per frame, previously duplicated in dcp.rs and reel.rs), `preflight::check_atmos_path`/`check_atmos_frame_count` (one Atmos file per picture frame), `preflight::check_reel_split_support` (3D, Atmos, `--hdr-dci` and markers have no place in a split composition), plus the parses that used to happen at wrap time: `subtitle::check_timed_text_readable` for `--subtitle` and `--ccap`, and `audio_map::parse_audio_map` against the WAV's own channel count. The frame count costs a full decode to probe, so the front end probes once and the plan carries the result. Checks that name a flag or a panel control (spelling parsers, flag pairings such as the audio map beside the upmix) stay in the front ends, since the two spell them differently.
- Hints are advisory, never refusals: everything they name builds and packages. `hints::gather_hints` probes the plan (loudness through postkit, cues through `subtitle::load_styled_cues`) into a `HintFacts`, and the pure `hints_from` turns that into text, so every threshold is a named constant the tests drive directly. The set is DCP-o-matic's projector-facing list: Interop chosen; a sound track packaged with fewer than 6 channels, or with a count that is neither 8 nor 16; the stereo upmix; Scope content in a Flat container, content narrower than 1.90 in a Scope container, and a container that is neither Flat nor Scope; a video bit rate at or above 245 Mbps; 25/30/48/50/60 fps (with the halved rate to fall back to, and the extra advice for Interop at 25); 4K 3D; a source-to-DCP speed change past 25.5/24; audio true peak above -3.0 dBTP; sound with no language; a SMPTE feature with no FFEC and FFMC markers, and a marker at or past the picture length; and per cue file, a first subtitle before 4 s, a cue under 15 frames, a gap under 2 frames or an overlap, more than 3 lines, a line over 52 characters (replaced by the stronger hint at 79), plus for closed captions a line over 32 characters, more than 3 lines and, on Interop, overlapping captions. Each rule speaks once for the whole job, naming the file and the first offending cue's time. The CLI prints them as `hint:` warnings before the encode and `create --check` stops there; the GUI's `submit_job` returns them instead of queueing until the panel resends with `hintsAccepted`, and the job log lists them when the build proceeds.
- Source picture processing (`create`, CORE/source_picture.rs, postkit picture_processing.rs): per-side crop (`--crop-left/--crop-right/--crop-top/--crop-bottom`, source pixels before any rotation), black-border detection (`--auto-crop` with `--auto-crop-threshold`, cropdetect over 8 seeked frames whose content rectangles are unioned), fill crop (`--fill-crop`, `Crop::to_aspect` toward the fit box, taken the other way round when a quarter turn follows it), `--deinterlace`, `--denoise`, `--rotate 90|180|270` and `--flip horizontal|vertical|both`. `resolve_picture` turns the flags plus an `EncodeGeometry` into one postkit `PictureProcessing`, and the plan it produces is the only place sizes come from: the CLI joins the plan's filters into the decode's `-vf` and slices the raw stream at the plan's output size, the GUI hands the same processing to `EncodeRunOptions.picture`, and a still gets the same filter chain on its own one-frame ffmpeg decode. The three ways of choosing a crop refuse each other by name. Order is deinterlace, denoise, crop, rotate, flip, scale, pad, and a video fade is appended after all of it.
- Automatic source fitting (`create --twok`/`--fourk`): the fit box is the container's active area when `--container`/`--container-dims` gave one, else the forced raster itself, and the picture is scaled into that box preserving aspect and centred on the forced raster with black around it. So `--twok --container 2k-scope --fill-crop` on a 1920x1080 source crops to 1920x804, scales to 2048x856 and pads to 2048x1080, and the CPL declares a 2048x1080 stored area with a 2048x858 active area. Without a forced raster nothing is scaled and the encode raster is whatever the crop and the rotation leave, which is what an unflagged create always did. This replaced `check_encode_raster`, which used to refuse any source that was not already the forced raster. The GUI names a container rather than a raster, so it only forces one when Fill container is ticked. J2K directory input is refused for any of these flags before the encode, since nothing decodes there.
- Background/pad colour (`create --pad-color <RRGGBB>`, dom#1042): the head/tail pad frames are filled with a caller-given sRGB colour instead of black. The colour runs through postkit's real Rec.709 RGB -> DCI X'Y'Z' DCDM transform (`colour::rgb_to_xyz_inplace`) before J2K encoding, so the stored codestream carries correct X'Y'Z' code values (verified: a decoded pad frame's XYZ matches an independent Rec.709->XYZ+2.6-gamma computation within 1 code value). Note: grok's `apply_xyz_transform` cparameter works (an earlier inert reading came from a stale cached grokj2k-sys build; run `cargo clean` if colour output looks wrong). `create --video` sets it true for SDR sources and for the generic tonemap branch, and false on the HDR-LUT branch (the LUT already outputs X'Y'Z'). Pad frames use postkit `colour::rgb_to_xyz_inplace` with the flag off. grok's transform and postkit's differ slightly (red: [2817,2183,870] vs [2914,2258,898], different linearization), both valid X'Y'Z'; harmonizing them is an open todo.
- Reel splitting (`create --reel-length <minutes>`, reel.rs): splits the encoded frame sequence, audio and subtitles into per-reel ranges and wraps one picture/sound/subtitle MXF set per reel, then emits a multi-reel CPL over a shared PKL/ASSETMAP. Boundaries are in whole frames at the edit rate; audio is sliced sample-accurately (frames * sample_rate/fps) and padded to the reel frame count; DCST cues are re-split by reel and rebased to reel-local time. Every reel is at least 1s (a sub-second remainder merges back). postkit's wrapper consumes every input file, so picture is wrapped from an explicit per-reel file list and audio/subtitle from temp files. The single-reel path (flag absent) is unchanged.
- Explicit reel splits (dom#2964): `create --split-at <tc>[,<tc>...]` splits at HH:MM:SS or HH:MM:SS:FF timecodes (converted to frame boundaries); `create --split-chapters` (and `pipeline --split-chapters`) read the source's chapter marks via `ffprobe -show_chapters`. Both feed explicit frame boundaries into the same multi-reel path as `--reel-length` (audio/subtitle split identically), and reject any boundary that would make a reel shorter than 1s. `--split-at` and `--reel-length` are mutually exclusive.
- Input decode range (`create`/`pipeline --input-range full|legal`): forces the source's decode range instead of trusting its metadata, correcting wrong or absent range flags. postkit's raw-RGB ffmpeg decode is frozen, so the correction re-decodes the source into a lossless FFV1/gbrp16le intermediate with `scale=in_range=<full|tv>:out_range=full` and the encode reads that. Video input only.
- Disk writer (`format-drive`, `check-drive`, disk.rs, dom#2095/dom#2112): `format-drive <target> --fs ext2|ext3 [--label] --yes [--image]` shells out to mkfs.ext2/ext3 (`-L` label). Safety: it refuses any target that (or whose partitions) appear in /proc/mounts, requires `--yes`, and without `--image` requires a block device (`--image` allows a regular file for tests/loopback). `check-drive <target>` reports the filesystem type and label without modifying, via `blkid -o export` when present, else by parsing the ext superblock directly (magic 0xEF53 at 0x438, journal/feature flags to tell ext2/3/4 apart, label at 0x478) so it works unprivileged on image files.
- HFR frame rates (hfr.rs): legal SMPTE rates 24/25/30/48/50/60/96/100/120 (Interop 24/25/30/48); 4K is capped at 30 fps per the DCI HFR addendum. `create_dcp` and the CLI/GUI pipelines reject an illegal fps/resolution combo loudly before encoding; the edit rate threads through both CPL and MXF. A 24000/1001 (23.976) source maps to the 24 fps edit rate by playing 0.1% faster, with a 1000/1001 audio pull-up applied before PCM wrapping. `hfr::conform_source_to_dcp` is the single decision behind that, returning the rate the picture is read at and whether the sound needs the pull-up, and `hfr::audio_pull_up` runs the pull-up itself: the CLI create path, the CLI `pipeline` path and the GUI all go through the pair. The read rate reaches ffmpeg as postkit's `read_source_at`, an input `-r` before `-i`, so the `fps` filter of the same rate passes every frame through instead of duplicating one every 1001. The create path decodes with no `fps` filter at all, so it only needs the pull-up half. The encode seams themselves take postkit's rational `encode::FrameRate` (`EncodeRunOptions.fps`, `StreamEncodeOptions.fps`, `write_image_concat_list`, `StillHold.fps`, `subtitle::prepare_subtitle_burn`), so a rate reaches ffmpeg's `fps` filter as `24000/1001` rather than as `24`. Every one of them is handed `FrameRate::whole(rate)` here, because a DCP edit rate is a whole number and both front ends carry it as one. The rational source rate is still read: `hfr::source_rate_to_dcp` maps it onto the edit rate and flags the pull-up, and `hints::gather_hints` measures the source-to-DCP speed change against it.
- ISDCF content title (isdcf_title.rs over isdcf_name.rs, `create --isdcf-name`, GUI Settings "Name DCPs by the ISDCF convention"): one function maps a `DcpConfig` plus the naming options onto `isdcf_name`'s input, so the CLI and the GUI name a package identically. Everything the name spells comes from what the package carries: content type, version number, chain, 3D, luminance, rounded frame rate, container aspect, audio language, open and closed text languages, territory and its first rating, channel ladder, Atmos, resolution, studio, date, facility, standard and OV/VF. The channel ladder is read from the packaged WAV's channel count the way `cpl::main_sound_configuration` reads it (2 -> 20, 6 or 16 -> 51, 8 -> 71, anything else MOS, HI/VI outside the main layout), so the CLI names after the audio is prepared, not before. Burnt-in subtitles are spelled in lower case and open ones in upper: a burnt package registers no timed-text track, which is the signal, and a registered track wins when both are present. Without `--container` the config declares no container, so the aspect comes from the coded raster read back from the first codestream (the CPL declares the same raster as the active area). With no frames to read either, it falls back to flat. `--output` is untouched by the naming, and the GUI moves only an output folder it derived from the title itself.
- CPL ratings and content version (cpl.rs, dcp.rs, reel.rs): `create --rating AGENCY=LABEL` (repeatable, split on the first '=' because an agency is a URI carrying colons) fills the ST 429-7 `RatingList`, and the first `create --content-version` becomes the `ContentVersion` LabelText (postkit writes the title when there is none). Both reach the single-reel and the reel-split CPL. `create --audio-lang` is carried on `DcpConfig` for the name, but it does not reach the sound MXF's MCA labels, whose `RFC5646SpokenLanguage` is asdcplib's hard-coded `en-US` default (see DESIGN_TODO).
- CPL markers (markers.rs, cpl.rs): every created composition carries a ST 429-7 `MainMarkers` asset at the head of reel 1's AssetList (the schema orders the list), inline with no PKL/ASSETMAP entry and at the picture's edit rate. The default set is FFOC=1 and LFOC=duration-1, which is what libdcp's Bv2.1 verifier and dcpdoctor check; `create --marker LABEL=timecode` (repeatable) replaces it with any of the ten defined markers, validated against the composition length. Split compositions take the default pair only, since a marker offset is relative to its own reel. The `markers` subcommand prints the same MarkerList XML. `markers::markers_from_cpl` is the read side, so the paths that re-author a CPL around an existing composition (`decrypt`, `transcode-dcp`) carry the marker track through instead of dropping it; it ignores the Label's optional scope attribute so CPLs from other tools parse.
- Head/tail padding (`create --pad-head <dur> --pad-tail <dur>`, pad.rs): duration is frames (`48f`) or seconds (`2s`); a bare number or a fractional-frame seconds value is rejected. One black (or `--pad-color`) frame is encoded once and its codestream repeated for every padded frame; audio extends with sample-accurate silence at frame edges; head padding slides supplied SRT cues by the head offset and keeps FFOC/LFOC correct. Rejected loud (each a broken DCP): padding with `--reel-length`, 3D (`--right-eye`), Atmos (`--atmos`), or head padding with a supplied SMPTE subtitle XML.
- Head/tail trim (`create --trim-start <dur> --trim-end <dur>`, trim.rs): same duration syntax as padding, and applied before it, so `--trim-start 2s --pad-head 1s` drops two seconds and then prepends one. A source the encoder reads is windowed rather than trimmed afterwards: `trim::encode_window` turns the trim into a postkit `FrameRange` and the encoder compresses those frames and no others, so a five-minute keep out of a two-hour source costs five minutes of encoder time. That one function is what decides, so the command line and the GUI cannot answer it differently, and both eyes of a 3D job take the same window. A codestream directory is never encoded, so its kept frames are still hardlinked into a fresh directory renumbered from zero by `link_trimmed_frames`, and so is a source whose length was never probed. Audio is sliced sample-accurately, after any 23.976 pull-up, whose resample changes what a frame of audio is worth. Timed text is the only thing that still carries the source's timing, so `DcpConfig::source_trim` (head frames plus the frames that survived) reaches the DCST conversion, where a cue wholly outside the kept window is dropped, one straddling a boundary is clamped and the rest slide back. Trimming a supplied SMPTE subtitle XML is refused, like head-padding one: its authored timing is never rewritten.
- Still image input (`create --video <image> --still-length <dur>`, still.rs): a single image is a third input shape beside a video and a codestream directory. It is encoded once through the same grok pipeline as the pad frames and the codestream hardlinked for every frame of the hold, which a frame-wrapped picture MXF permits, so a two-minute card costs one encode. A still carries no length of its own, so `--still-length` is required for one and refused for anything else, and `--trim-start`/`--trim-end` are refused on a still (shortening the hold is the same thing).
- Source colour space (`create --source-colourspace`): the flag says what the source carries, and `encode::xyz_route` turns that into one of three routes to X'Y'Z'. `rec709` (the default) leaves grok's `apply_xyz_transform` on, byte-identical to before the flag existed; `xyz` turns it off; `p3`, `rec2020` and `logc` carry a postkit `DcdmTransform` into `CompressParams.source_transform`, which converts every frame on the encoder threads with grok's transform off (verified: a solid P3 frame encoded through the route and decoded with grk_decompress lands within one code value of an independent computation over the RP 431-2 P3 matrix, P3 red reaches further than Rec.709 red instead of matching it, and a LogC3 grey card frame at code 0.391 lands within one 12-bit code of the Rec.709 frame carrying 0.18 scene linear). ACES and ACEScg stay refused rather than routed through a matrix that cannot express them: they are scene-referred, so they need a rendering transform, and the refusal names both the `--hdr-to-dci-lut` route and converting to X'Y'Z' first. Any space but the default is refused for a J2K directory, where the picture is already encoded and no transform can run. The flag and the HDR source flags both decide the same transform, so setting both is refused.
- J2K quality target (`create --quality-psnr <dB>`, the GUI's Quality (PSNR dB) field, `encode::video_codestream_byte_cap`): grok allocates layers to that PSNR instead of to the ratio `encode::video_compression_ratio` computes, and the bandwidth becomes a per-frame byte cap rather than what the allocation aims at. The cap is the smaller of the cap that already applied (the DCI one, or the HDR Addendum's under `--hdr-dci`) and the bytes the bandwidth allows at the edit rate, which 3D halves per eye the way the ratio is doubled per eye. postkit compresses a frame the target pushes over the cap again by ratio, so no codestream passes it. The target is at least 20 and at most 80 dB, refused outside that before anything is encoded.
- Picture findings (postkit `picture_findings.rs`): ffmpeg's `blackdetect` and `freezedetect` run on a branch of postkit's decode and the black and frozen runs come back on `pipeline::EncodeResult`. `PictureFindings::describe(fps)` writes the wording both front ends print, `pipeline` as a `black picture from 00:00:00:00 to 00:00:02:23 (frames 0 to 71)` warning and the GUI job log as the same line under `[ENCODE]`, the right eye's prefixed `right eye:`. `create` compresses through `grok_encoder::encode_video_pipeline_resumable`, which decodes with ffmpeg's stderr closed, so it reports none (DESIGN_TODO).
- Audio channel mapping matrix (`create --audio-map`, CORE/audio_map.rs, postkit audio_mix_matrix.rs): comma-separated `IN:OUT` or `IN:OUT@GAIN` entries route any source channel to any DCP lane at a gain in decibels, summing where several inputs land on one lane. OUT may be a lane name from `audio_route::channel_index` (case-insensitive) as well as a 1-based number, and the output width is the highest lane named, widened to the smallest layout the sound wrapper takes (2, 6, 8 or 16), since nothing in DCP has a three-channel track. Mixing is postkit's `mix_wav_files`, in f64 on the file's own sample values, so a routing with no gain reproduces its source samples bit for bit. The map runs before every other audio step, and it is refused beside `--audio-input-order lrc-ls-rs-lfe`, `--upmix` and a channel WAV directory, each of which decides channel placement its own way.
- Audio delay (`create --audio-delay <ms>`, audio_adjust.rs): a positive delay prepends silence and drops the same from the tail, a negative one drops from the head and appends silence, so the running time never changes and the sound still matches the picture duration the CPL declares. It runs after any upmix and before loudness normalisation, so normalisation measures the silence that actually ships. A delay at least as long as the programme is refused.
- KDM formulation and forensic marking (`kdm`/`kdm-batch`/`kdm-rewrap`): `--formulation` is an `Option`, so absent still derives the formulation from whether `--device-cert` was given (`kdm::resolve_formulation`), and an explicit choice that contradicts the device list is refused naming both flags. `kdm-batch` carries no device list at all, because a batch spans cinemas and one list cannot fit them all, so it refuses a device-listing formulation up front with that reason rather than letting the generic resolver tell the caller to pass a flag the command does not have.
- Supplemental Version File (VF) creation (`create-vf`): references the OV's real asset ids for unchanged reels, wraps replacement essence (or copies an already-wrapped MXF) and registers it under its real embedded asset id in CPL/PKL/ASSETMAP, carries an `<OriginalPackagingList>` marker so dcpdoctor detects a supplemental. Validating the VF with `--ov` resolves cross-refs; alone it yields the supplemental-OV-not-provided warning, not a hard cross-ref error. `--replace-picture`/`--replace-sound` swap essence tracks; `--replace-subtitle`/`--add-subtitle REEL=PATH` (with `--subtitle-language`) wrap an SRT (converted to DCST) or a supplied SMPTE XML (unchanged) into a per-reel timed-text MXF and set the reel's MainSubtitle. A subtitle-only VF references the OV picture/sound by id and ships only the new subtitle MXF, so it can be authored from the OV's CPL/PKL/ASSETMAP without the OV essence (dom#1062).
- Assemble OV from existing DCPs (`assemble --input <dcp>... --output --title`, assemble.rs, dom#1675): builds one new composition (single CPL) whose reels are the inputs' reels in order (e.g. short + feature). Every referenced MXF is copied byte-identical and referenced by its existing asset UUID; a fresh CPL/PKL/ASSETMAP/VOLINDEX is written. Inputs must agree on standard, edit rate and picture resolution, else it fails loud listing the mismatch. Encrypted inputs are refused because a new CPL id would break the KDM's CPL binding.
- Edit DCP metadata (`edit --input [--output] [--title] [--annotation] [--content-kind] [--issuer]`, edit.rs, dom#1127): postkit's `package_edit::edit_package` does the rewrite, so a DCP and an IMF composition are retitled by the same code; edit.rs is the CLI's shape of it, an exit code and the log lines the GUI's retitle reads. It rewrites the single CPL's title / annotation / content kind / issuer in place (or into `--output`, copied first), assigns a new composition id, and refreshes the CPL's PKL and ASSETMAP entries (new id, new hash/size). Essence MXFs and their asset ids are untouched. Encrypted DCPs are refused (the KDM binds the CPL id). Setting a field the CPL does not carry is an error rather than a silent no-op. Metadata fields only; the digest's reel reorder/length edits are out of scope.
- Combine DCPs into one volume (`combine <dcp-dir>... --output`, combine.rs, dom#2019/2026/2027/2420): copies every asset byte-identical, writes one merged ASSETMAP/VOLINDEX and (default) one merged PKL; CPLs are never rewritten (cross-refs are by uuid, only ASSETMAP `<Path>` changes), so signatures/hashes and KDMs stay valid on encrypted inputs. `--separate-pkls` keeps each input PKL; `--sort` orders CPL entries by content title; `--annotation` sets the merged PKL/ASSETMAP AnnotationText (else derived from CPL titles). Dedupes on shared id + identical hash; same id + different hash is a loud error; root filename collisions rename on disk (ASSETMAP `<Path>` only). Interop loose subtitle assets (XML + font + PNG) relocate into a per-CPL subdirectory with only the `<Path>` updated, keeping the subtitle XML's relative font refs intact.
- Multi-composition package (`create-multi --compositions <manifest>`, multi_cpl.rs `create_multi_composition`): one CPL per manifest entry, each with its OWN picture/audio/subtitle, over one shared PKL/ASSETMAP. The manifest is a JSON array of `{title, j2k_dir, audio?, subtitle?, subtitle_language?, kind?}`. Single reel per composition. Contrast `create --versions`, which writes several CPLs over one SHARED essence set. Reuses the same wrap primitives (mxf_wrap, the versions.rs sound/subtitle helpers); with `--encrypt` it writes one key bundle per CPL.
- Encryption: content keys generated with the OS CSPRNG, essence AES-128 encrypted at wrap time (`postkit::mxf_wrap`, HMAC per SMPTE), PKL/ASSETMAP hashes taken from the final encrypted files, KeyIds written into the CPL. `create --encrypt` requires `--key-out <path>` (clap-enforced); the plaintext keys are written only there, never next to the DCP. The GUI mirrors this: encrypting requires a Key Output File. Every essence is encrypted: picture (MDIK), sound (MDAK), subtitle and closed caption (MDSK) and the Atmos aux-data track (MDEK), each with its own key minted through `versions::mint_key`. The AuxData block carries its KeyId too, and the keys file holds all of them, so the KDM `kdm` builds covers the whole composition and no validator sees a partially encrypted package.
- DCP signing (`--signer-cert/--signer-key/--signer-chain`, package_signature.rs) on `create`, `create --versions`, `assemble`, `create-vf`, `create-multi`, `combine`, `ingest-package` and `conform`; `combine` and `ingest-package` sign only the packing list they generate, because they hash CPLs rather than rewriting them, so a signature a CPL already carries stays valid. Signed CPLs and PKLs carry the optional `<Signer>` beside `ds:Signature` (postkit `dcp_signer_element`), the shape real Clipster and Doremi packages use: `ds:KeyInfoType` wrapping a `ds:X509Data` with the signing certificate's `ds:X509IssuerSerial` and no `X509SubjectName`, `xmlns:ds` declared locally, written before signing so the enveloped reference covers it and editing it breaks the signature. The signature profile follows the document's own root namespace, Interop signs rsa-sha1 with SHA-1 reference digests and SMPTE rsa-sha256 (postkit `SignatureProfile`), so repackaging paths that never see `--standard` get it right too. The chain is held to ST 430-2 at sign time by `dcpdoctor_core::cert_rules::check_certificates` over the chain as `ds:KeyInfo` embeds it (signature algorithm, RSA 2048 with e=65537, BasicConstraints and KeyUsage per role, signer role token distinct from the CAs', dnQualifier thumbprint, one Organization): a violation names the rule and nothing is written, and there is deliberately no opt-out flag, since a DCI verifier applies the same rules to the finished package anyway. `edit` strips the signature and Signer from every document it rewrites.
- SMPTE (and Interop) KDM generation, batch, DKDM rewrap (real signed ETM). `kdm --keys <key-out file>` binds the KDM to the DCP's actual image (MDIK) and audio (MDAK) content keys. `kdm --format smpte|interop` (also on `kdm-batch`) selects the ETM: Interop uses postkit's digicine 134-byte block, legacy output that needs real-gear validation. `kdm-batch` takes repeated `--cert` or a `--cert-dir` of cinema certs and writes one signed KDM per recipient. `kdm --device-cert <pem>` and `kdm-rewrap --device-cert <pem>`, repeatable, name the Trusted Device List (postkit `device_cert_files`): every KDM carries AuthorizedDeviceInfo, an empty list is the DCI assume-trust thumbprint, and naming any device replaces that thumbprint so the KDM plays only on the devices listed. `kdm-batch` has no such flag on purpose, one device list spanning cinemas would tie every recipient to someone else's gear. Certificate chain generation and inspection.
- Decrypt (`decrypt --input --output`, decrypt.rs): turns an encrypted DCP into a cleartext DCP of the same reel structure. Content keys come from a KDM plus the recipient RSA private key (`--kdm --recipient-key`, unwrapped via postkit `unwrap_kdm`) or the DCP's KEYS.json (`--keys`); one of those two sources is required. Each encrypted essence MXF is read through asdcplib's AES decrypt + HMAC context keyed by the MXF's own cryptographic_key_id, so a wrong key or a KDM that does not cover a KeyId fails loud (the OAEP unwrap, or the per-frame MIC, rejects it); non-encrypted assets copy byte-identical. The output CPL drops all KeyId/encryption elements, so it gets a new CPL id with fresh PKL/ASSETMAP/VOLINDEX hashes. Picture, sound and Atmos are read frame by frame; a timed-text track is read as its document plus every ancillary resource, and rewrapped with the same document, duration and resource ids, so the ResourceID a player matches survives. Rewrapped picture and sound get a new asset UUID, so the decrypted package is fresh rather than a byte-identical structural clone; timed text and aux data keep the id the source declared, which is what a supplemental package references. Key material stays in memory only, never in logs, errors or temp files. Every essence `create --encrypt` writes round-trips back to cleartext, and a track whose KeyId no key covers fails loud naming the asset. Both this path and transcode-dcp ship the source's own sound MXF, so `cpl::main_sound_from_cpl` carries the source CPL's `MainSoundConfiguration` and `MainSoundSampleRate` into the rebuilt CompositionMetadataAsset rather than writing no block; `vf` and `assemble` can replace or combine sound and write none.
- Encrypted-source transcode (`transcode-dcp --kdm --recipient-key | --keys`): the same key sources let transcode-dcp decrypt each source picture frame in memory before grk_decompress, then re-encode and rewrap cleartext exactly as the plaintext path; sound, timed text and Atmos go through the decrypt path so the cleartext output stays coherent, and the closed-caption and Atmos tracks are carried into the output CPL rather than dropped. Without key material an encrypted source is refused loud. The J2K temp frames written during transcode are plaintext by design.
- KDM distribution (cinema.rs, kdm_log.rs, kdm_template.rs, flm.rs, email.rs, cert_fetch.rs; shared helpers in store.rs). State files live under the XDG data dir (`~/.local/share/dcpwizard/`), each overridable per command, all written atomically (temp + rename):
  - Cinema/screen database (`cinemas.json`, `--db`). A cinema has contact emails and notes; each screen holds a recipient certificate as a file path or inline PEM, with the cert serial, SHA-1 thumbprint and subject cached for search. No private key material is stored. `cinema add|list|remove|add-screen|remove-screen|search|import-flm`; search matches cinema/screen name or cert serial/thumbprint substring. `kdm-batch --cinema <name>`/`--screen <cinema>/<screen>` resolves recipients from the db (inline certs are materialized to temp files); `--cert`/`--cert-dir` still work.
  - History log (`kdm-history.jsonl`, `--history-file`): every successful `kdm`/`kdm-batch` appends one JSON line of metadata only (UTC timestamp, CPL id, title, recipient subject + serial, validity window, output path, format) — never key material or KDM bodies. `kdm-history` lists and filters by title, recipient or date range.
  - Validity templates (`kdm-templates.json`): a named relative window = optional start offset from now + duration, emitted in a chosen UTC offset. `kdm-template add|list|remove`; `kdm`/`kdm-batch --template <name>` expands the window, and an explicit `--valid-from`/`--valid-to` overrides it. Expansion produces absolute ISO timestamps that flow through the same window resolution as a directly supplied window.
  - FLM-x import (`cinema import-flm`): parses an ISDCF FLM-x / SMPTE ST 430-7 FacilityListMessage (roxmltree, matched on element local names so the schema revision need not be pinned), taking the facility name, contact emails and one screen per device with its recipient (leaf, non-CA) X.509 certificate. A non-FacilityListMessage root fails loud.
  - Email delivery (`kdm`/`kdm-batch --email-to --smtp-config`, lettre 0.11 over rustls): the SMTP config is a TOML file (host, port, security tls/starttls/none, username, password, from, optional subject/body templates with `{title}`/`{cinema}`); the password is redacted in Debug and never logged. `kdm-batch --cinema` sends one email per cinema, its KDMs zipped, to the cinema's contact emails plus any `--email-to`; `--email-only-additional` sends only to `--email-to`.
  - `cert-fetch --vendor --serial [--type] -o` downloads a recipient certificate and validates it as parseable X.509 before writing. Supported endpoints are the credential-free public FTP servers: dolby/doremi (`ftp://ftp.cinema.dolby.com/Certificates/<first3>xxx/`, the `*-<serial>.cert.sha256.pem` leaf) and qube (`ftp://certificates.qubecinema.com/SMPTE-<type>/`). Other vendors error, telling the user to obtain the cert from the vendor. FTP transfer shells out to the system `curl` binary; the serial is validated to alphanumerics and passed as an argument, never through a shell.
- TMS upload (postkit's `tms` module behind its `tms` feature, `tms <package-dir> [--tms-config]`, `create --upload-to-tms`, DCP-o-matic's `tms_protocol`/`tms_ip`/`tms_path`/`tms_user`/`tms_password`/`upload_after_make_dcp`): every file under the package directory is put into `<path>/<package dir name>/` on the TMS, remote directories created before the files that go in them, one `[n/total] Uploaded` line per file, and the first failure stops the upload naming the file and the remote path it was going to. The config is a TOML file read like the SMTP one (protocol ftp|sftp, host, optional port defaulting to 21/22, path, user, password), with the password redacted in Debug, never logged and never an argument. tms_upload.rs is what stays here: the default path `~/.config/dcpwizard/tms.toml`, which carries this app's name, and the TOML read itself, which postkit deliberately does not do. Protocol handling sits behind one `TmsTransport` trait (`ensure_dir`, `put_file`) with an ssh2/libssh2 implementation, a suppaftp one, and a fake the layout tests drive, so nothing in the test run touches a network. sftp checks the host key against `~/.ssh/known_hosts` and refuses an unknown or changed key, printing the SHA256 fingerprint and the `ssh-keyscan` line that would record it: libssh2 verifies nothing by itself, so without that the password goes to whatever answers on the address. ftp warns that the login and the package cross the network in the clear. `create --upload-to-tms` reads the config before the encode, so an unusable one fails in a second rather than after an hour, and uploads only after a clean build, before `--shutdown-when-done` powers the machine off.
- Stereoscopic 3D (`create --right-eye`): both eyes encoded at the same settings, wrapped into one ST 429-10 picture MXF (postkit `wrap_stereoscopic`), CPL carries the `MainStereoscopicPicture` element (429-10/2008 namespace, EditRate = composition rate, FrameRate doubled). Validated against the clairmeta 429-10 XSD.
- Packaged sound layout (mxf_wrap.rs `prepare_packaged_channels`, `create --audio-channels 2|6|8|16`): one pass over the WAV reorders a six-channel source to canonical DCP 5.1 (`--audio-input-order lrc-ls-rs-lfe` remaps that common source order, it never guesses) and then fills the track with silent channels up to the count asked for. Without the flag a 5.1 source is widened to 16 and every other source is packaged at its own width, which is what the wrap has always done. A source wider than the count asked for is refused, at plan time by `preflight::check_audio_channels` and again at wrap time, since filling only adds silence and can never narrow a track: `--audio-map` folds channels instead.
- Sound the job did not name (audio_fallback.rs): both create paths open their audio chain with the picture source's own track. `audio_fallback::extract_embedded_audio` probes the source and, when it carries audio, writes it out as a 48 kHz 24-bit WAV that enters the chain where a named WAV would, so map, route, upmix, delay, loudness and pull-up all still apply. `create` does this with its own demux step (main.rs), the GUI's `prepare_audio` calls the helper. With no audio from either, dcp.rs `silent_sound_fill` gives a SMPTE build `audio_fallback::write_silent_wav` silence as its prepared audio, as long as the picture and 5.1 wide unless `--audio-channels` says otherwise, so the composition carries a sound track in every reel and can carry the CompositionMetadataAsset, which holds MainSoundConfiguration and is therefore unwritable without one. Interop requires neither and stays picture only. The fill lands before the single/multi-reel split, so the reel splitter and library item reels see it as ordinary audio, and it is deleted with the other audio intermediates once the package is written.
- MCA channel labeling: labels follow the content, counts follow the container. `mxf_wrap::build_mca_config` and `cpl::main_sound_configuration` take the channels the content fills (2 -> stereo/`20`, 6 -> 5.1/`51`, 8 -> 7.1/`71`) and the channels the track is packaged with separately, so the silent fill channels get '-' placeholders instead of joining the soundfield group: stereo filled to 16 is `20/L,R,-,...`, not `51/...`. dcp.rs probes the source for the layout and the prepared file for the width. 16 content channels still read as 5.1 because no content layout is that wide, so a caller that knows only the packaged count (the reel splitter, the versions packer, the wrap's own auto-derive) is looking at the filled 5.1 track. `create --hi-channel/--vi-channel` add standalone HI/VI-N labels outside the main layout.
- Dolby Atmos (`create --atmos`): wraps a Dolby Atmos / DCData bitstream (`EssenceType::Atmos`) and registers a ST 429-18 `AuxData` element (Dolby `2012/AD` namespace, IAB UL) in CPL/PKL/ASSETMAP. Structure validates; real conformance needs real Atmos essence.
- Sign-language video (`create --sign-language-video <file> --sign-language-lang <rfc5646>`, sign_language.rs, dom#1602, ISDCF Doc 13): the input is encoded to VP9 (480x640, 24 fps, ~576 kbps, yuv420p, 2s chunks via ffmpeg webm_chunk) and packed into 288,000-byte PCM blocks (20-byte big-endian header MARKER/Lv/Lb/Le/MARKER + webm header + VP9 segment + null pad) carried on channel 15 of the 16-channel MainSound track. asdcplib's MCA parser labels channel 15 SLVS (UL 06.0e.2b.34.04.01.01.0d.0d.0f.03.02.01.01.00.00, per-channel language `SLVS:<lang>`, needs a trailing channel-16 token so the language applies), and the CPL CompositionMetadata carries the `http://isdcf.com/2017/10/SignLanguageVideo` ExtensionMetadata with the Language Tag. Packing verified against the ISDCF reference encoder; channel/UL/CPL against libdcp. The MCA read-back exposes only counts (main + 1 SLVS channel), not per-channel ULs: that is a limit of the pinned asdcplib, whose `pcm::MxfReader::mca_label_subdescriptors` returns per-channel tag symbols and label ULs from 4f137a0 onward.
- conform (postkit conform.rs, CORE conform.rs, aaf_import.rs, libaaf-sys): CMX3600 EDL, FCP7 xmeml, FCPX fcpxml, OTIO and AAF parse to one `Timeline`, and `--media-dir`/`--output` drives the reel plan to a finished multi-reel DCP. fcpxml resolves connected clips in lanes, compound clips, nested and sync clips and connected storylines onto the record timeline through a recursive placement walk; OTIO parses in postkit (per-track record positions, reel names from the media target_url basename); AAF reads through libaaf (extern/libaaf submodule, static build via the libaaf-sys shim, which flattens the object graph to tracks and items so Rust never mirrors a libaaf struct; libaaf-sys builds the aaf-static cmake target and copies the archive out of the build tree because libaaf installs only on Linux and names the archive per platform; reads are serialized behind a mutex in `AafComposition::read` because concurrent libaaf reads corrupt the heap). Constant AAF clip gain lands on `EditEvent.gain_factor` (unity collapses to None, a muted clip becomes 0.0) and reaches the conformed audio as ffmpeg `-af volume`; gain automation, pan and mute are surfaced in `Timeline.skipped`, not applied. Anything with no source clip behind it lands in `Timeline.skipped` with a named reason (titles, generators, captions, transitions, multicam angles, auditions, essence libaaf cannot resolve), nothing is dropped silently.
- verify/info/report via dcpdoctor-core; SRT to subtitle-XML conversion; supplied SMPTE subtitle XML is wrapped unchanged, preserving authored placement and styling. Subtitle/watermark burn-in is separate.
- Subtitle input formats + authoring (subtitle.rs, W6): `create --subtitle` accepts `.srt`, `.ass`/`.ssa` (dom#1462), `.pac` (dom#1719, Latin codepage), `.mks`/`.mkv` (dom#3131, via ffmpeg), `.fcpxml` (dom#2909) and an Interop `DCSubtitle` XML with PNG bitmap subs (dom#1376); a supplied SMPTE DCST XML is still wrapped unchanged. postkit's parsers produce `StyledCue`s; the styled DCST renderer carries per-run italic/bold/underline/colour as inline `<dcst:Font>` spans and per-cue alignment/position. Placement controls (dom#1729/#2796): `--subtitle-halign/--subtitle-valign/--subtitle-vposition` (top-anchored cues grow downward). 3D depth (dom#1359): `--subtitle-zposition` emits the ST 428-7 Zposition on every cue (the timed-text descriptor's Z-Position-In-Use flag is not set by the asdcplib writer). RTL (dom#860): `--subtitle-rtl auto|on|off` reshapes+reorders Hebrew/Arabic to visual order via postkit bidi. Wrap (dom#1626): `--subtitle-wrap <chars>` wraps overlong lines on whitespace via postkit wrap. Font (dom#1023): `--subtitle-font <ttf/otf>` subsets to the used glyphs (postkit font_subset, SMPTE 640 KB limit, fails loud over it; `--subtitle-no-subset` opts out) and embeds it in the timed-text MXF referenced by a `LoadFont` whose urn matches the embedded ancillary-resource id (postkit `MxfWrapOptions.resource_ids`). Without the flag a text track still embeds one, taken from `postkit::subtitle_raster::find_system_sans_font` so the packaged font is a face the burn path would also shape with, and refused loud when the machine carries none. ST 428-7 asks for a `LoadFont` wherever there is text, and a `Font` carries its `ID` only when a `LoadFont` introduced it, which is why the loose `subtitle` conversion command's output names none. A bitmap-only track embeds no font. Bitmap PNGs embed the same way with `<dcst:Image>` refs. Cross-reel font dedup (dom#2533): under reel splitting the font is embedded per reel MXF (SMPTE embeds fonts inside each timed-text MXF) but referenced by one shared asset id in every reel's XML. Under reel splitting every reel of a subtitled composition carries a timed-text asset spanning it, because a composition with subtitles needs a MainSubtitle on every reel; a reel no cue falls into carries the placeholder DCP-o-matic writes, one space from the reel start for a second, since ST 428-7 has no document without a cue in it. The wrap takes the reel's frame count as the essence duration rather than the last cue, so IntrinsicDuration and Duration match the picture. Appearance: `SubtitleOptions::appearance` (`TimedTextAppearance`) carries the ST 428-7 `Font` attributes and the fades that `--subtitle-font-size/--subtitle-colour/--subtitle-effect/--subtitle-effect-colour/--subtitle-fade-up/--subtitle-fade-down` name, each falling back to what the track has always carried (42 points, FFFFFFFF on a shadow of FF000000, a fade of fps/12 frames each way); a named fade rounds its milliseconds to whole frames at the reel's edit rate. An outline is written `border`, the spelling ST 428-7 and libdcp use for it. Colours are held as ARGB hex and the effect as its attribute spelling, because postkit's `Rgba` and `BurnEffect` carry no serde derives and this rides along with the rest of `SubtitleOptions`. The appearance reaches the open `--subtitle` track only: `--ccap` wraps through `SubtitleOptions::default()`, and `create --versions` renders its per-version subtitles through the same writer under the same defaults: the frame-based callers convert their cues to `StyledCue`s (rounding the millisecond up so the renderer's own truncation lands back on the frame it came from) and there is one SMPTE writer. The GUI exposes the same six fields. Conformance the packaged document and CPL carry, each read by a dcpdoctor rule: one namespace on the root, a zero `StartTime` after `TimeCodeRate`, an `IssueDate` written `yyyy-mm-ddThh:mm:ss` with no timezone, the MXF ResourceID equal to the document's `<Id>` and distinct from the track file's asset id (postkit reads it out of the XML at wrap time), and a `<Hash>` on the reel's MainSubtitle and closed caption alongside picture and sound. The closed caption is written `<tt:ClosedCaption xmlns:tt="http://www.smpte-ra.org/schemas/429-12/2008/TT">` with a `<tt:Language>`, the element ST 429-12 declares and the form the ISDCF Bv2.1 test DCP and libdcp both write: 429-7's reel AssetList takes only a foreign-namespace element after MainSubtitle, so the same asset in the CPL's own namespace is a schema violation. Its other children come from 429-7's TrackFileAssetType and stay unprefixed. Verified end-to-end: ass/font/interop-png creates pass dcpdoctor with 0 errors; the styled DCST validates against the ST 428-7 XSD.
- Standalone subtitle editing (`subtitle-edit`, subtitle_edit.rs, dom#828/#2071): `--list` cues, `--shift-ms` all cues, or `--index N` with `--text`/`--set-start-ms`+`--set-end-ms`, written back as SRT. Loads any parsable format; edits source files only, never subtitles inside a finished DCP.
- HDR source video requires `create --hdr-to-dci-lut <lut>`. `--allow-generic-hdr-tonemap` enables FFmpeg tone mapping with a warning, for explicitly accepted non-delivery use.
- Transcode/import via ffmpeg, frame extraction, dv-inject via dovi_tool, loudness via loudnorm.
- Create-time audio processing (audio_route.rs, loudness.rs, main.rs `prepare_create_audio`, applied to explicit `--audio` and to demuxed audio in both the video and J2K-dir branches): filename channel auto-routing (dom#2134) when `--audio` is a directory of mono WAVs (`name_L.wav`/`_R`/`_C`/`_Lfe`/`_Ls`/`_Rs`/... routed to canonical DCP lanes, missing lanes silent, non-mono or unknown suffix fails loud); stereo->5.1 upmix (`create --upmix a|b`, dom#921/#1080, postkit `upmix_wav`); loudness normalization (`create --loudness-target leqm=<db>|lufs=<v>` with `--true-peak-ceiling`, dom#1382, postkit `adjust_loudness`, refused loud if the gain would breach the true-peak ceiling). Order is map -> route -> upmix -> loudness, before pull-up and sign-language packing. Standalone `crossfade --a --b -o --overlap` (dom#374, equal-power join, postkit `crossfade_join_wav`) and `mid-side-decode -i -o --mid --side` (dom#3020, postkit `decode_mid_side_wav`) subcommands.
- Encode QoL on `create` (encode_qol.rs): `--start-at HH:MM|RFC3339|+offset` blocks until a wall-clock time before encoding (dom#2359); `--resume` reuses the on-disk J2K frame prefix via postkit `encode_video_pipeline_resumable`, guarded by a persisted `.dcpwizard-encode.json` that must match source+params (dom#344, survives restarts); progress prints a running average-fps ETA (dom#502); `--shutdown-when-done` powers off after a clean encode, resolved loud up front so a missing shutdown binary fails before the long run (dom#1394; never runs in tests).
- SQLite version tracker and dashboard (including serve), daemon/batch IPC, shell completion.
- Post-build actions (`gui/index.html` `post-build-actions`, `gui/src/main.js`): a finished build shows Play / Inspect / Reveal beside the progress bar, carrying the output directory on the row's dataset. Play calls guikit's `previewDcp`. Inspect switches to the Verify view, fills `verify-path` and calls the same `runVerification` the Validate button calls, rather than a second copy of it, so the report comes back with whatever strict / MXF / hash boxes that view has ticked. Reveal calls `revealItemInDir`. `beginBuild` hides the row, so a cancelled or failed build never leaves it pointing at a package that was not written. The in-build `validation-result` pill is left alone: Inspect always runs the Verify view, so the button means one thing whether or not the job was built with Validate ticked.
- Embedded preview (guikit `preview/`): the player draws into a native surface layered over the webview, one host per platform (linux a GtkGLArea, macos an NSOpenGLView over the WKWebView, windows a WS_CHILD window with wgl over the WebView2 child). The platform contract is three items, identical everywhere: `attach(&tauri::Window) -> Result<EmbeddedPreview, String>`, `EmbeddedPreview::player()` and `EmbeddedPreview::set_surface(x, y, w, h, visible)`. The preview header carries the QC overlays (safe area, aspect mask, centre cross, thirds grid as one mpv `vf` chain), the decode resolution (full/half/quarter through the J2K decoder's `lowres`), the crop overlay, the subtitle and CC render toggles, and a HUD of frame, fps, buffer depth and dropped frames read from the metadata poll.
- Accessibility check (`accessibility <dcp>`, CORE/accessibility.rs over postkit accessibility.rs): a structural probe over the package's elements and MCA tokens, reporting each track type present, absent or undeterminable against a chosen standard (cvaa|eaa|aoda|ofcom). Two are undeterminable by construction: nothing in a package declares burned-in open captions, and commentary is declared only by an ST 2067-2 CommentarySequence and can otherwise ride an ordinary audio track, so neither is ever reported absent.
- Job log timings (`gui/src-tauri/src/pipeline.rs`): `run_job` times preflight, encode, audio, package and validate with `Instant`, and `format_stage_timing` writes each as `[TIMING] <stage> took <m>m<s>s` next to that stage's own `[ENCODE]`, `[PACKAGE]` and `[VALIDATE]` lines, plus a `total`. The progress event is unchanged: its `elapsed_secs` already carries the encode's own clock from postkit.

## Not implemented (de-advertised)

These have no working path and are not advertised: DTS:X (blocked on a confirmed DataEssenceCoding UL, see DESIGN_TODO; the `MxfType::DtsX` variant was removed so it fails loud rather than emitting an Atmos UL). `cli_flags_test.sh` invokes each GUI command line and fails on clap parse errors.

Subtitle packaging into a DCP timed-text track is real: `create --subtitle` converts SRT/ASS/PAC/MKS/FCPXML/Interop-PNG to ST 428-7 DCST XML, and supplied SMPTE XML is wrapped unchanged. Both paths register the timed-text MXF in the reel/CPL/PKL/ASSETMAP. Placement, RTL, wrap, font embedding and 3D Zposition are wired (see the subtitle bullet above).

Burn-in during the encode is separate from that: `create --burn-subtitle` parses the same inputs to `StyledCue`s and hands them to postkit's `SubtitleBurn`, which composites them onto every decoded frame before the colour transform. Nothing is registered in the CPL, since the text is picture. `check_burn_supported` refuses the combinations that would draw in the wrong place before an encode starts: the same file as `--subtitle`, a J2K directory, and any route that hands the encoder X'Y'Z' already (`--source-colourspace xyz`, `--hdr-already-pq`, `--hdr-to-dci-lut`). P3 and Rec.2020 are fine, since the burn goes on in display RGB and the DCDM matrix converts it with the picture. A held still cannot link one codestream for the whole hold any more, so `StillHold` encodes one frame per run of frames sharing a cue set and links within the run. Appearance comes from postkit's `BurnStyleOverrides`, laid over `BurnStyle::default()` inside `prepare_subtitle_burn`: `--burn-font-size` (percent of frame height, default from `DEFAULT_FONT_SIZE_RATIO`), `--burn-colour`, `--burn-effect none|outline|shadow`, `--burn-effect-colour`, `--burn-outline-width` (percent of text height, default from `DEFAULT_OUTLINE_WIDTH_RATIO`), `--burn-line-height` (multiple of the text height, default from `DEFAULT_LINE_HEIGHT_RATIO`), `--burn-margin` (percent of the frame height from the anchored edge, default from `DEFAULT_MARGIN_RATIO`), `--burn-x-scale`, `--burn-y-scale`, `--burn-fade-up` and `--burn-fade-down`. postkit owns the parsing and the range checks, so a bad value is refused there and reported under the flag's own name before an encode starts, as is any appearance flag given without the track it styles. The GUI has the same controls except `--burn-x-scale` and `--burn-y-scale`.

Deleted (dead, zero callers): dcp_diff, plugin, preferences, geometry, and the prores re-export shim.
